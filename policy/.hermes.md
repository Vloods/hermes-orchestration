# Project orchestration policy

This file applies when an agent is launched in this project workspace. It is not a global Hermes config, and a Kanban worker in an isolated scratch/worktree will not automatically inherit it unless that workspace contains the file or the task explicitly carries the relevant policy.

## Decision ownership

The agent receiving the user's original request is the supervisor and final decision maker. Correctness is mandatory; then minimize reactivations, context consumed by the supervisor, coordination cycles, and unnecessary worker compute. Delegation transfers execution, never accountability.

## Choosing a mechanism

Do small, bounded changes directly. Use deterministic tools for searches, counts, transforms, and checks. Delegate one substantial bounded objective to one worker when it can independently inspect, implement, test, fix, and return a compact report. Add workers only for genuinely independent workstreams; avoid overlapping edits. Use Kanban for durable asynchronous work, named roles, retry/review, and human handoffs—not for a trivial lookup. Escalate difficult correctness, security, concurrency, or architecture decisions to a real solver route only when that route is available.

## Worker contract

Each assignment names scope, acceptance criteria, permitted writes, constraints, verification, and expected output. A worker owns execution through validation and returns one concise evidence-backed result. Escalate only a blocker changing scope, architecture, security, permissions, or correctness; do not send routine progress updates. After two non-converging correction attempts on the same failure, report evidence rather than guessing.

## Verification and reporting

The supervisor reconciles outputs with real files, tests, and board state before claiming completion. Prefer targeted verification to repeating a worker's entire investigation. A finished report states the outcome, tests, changed paths, and meaningful risks; distinguish confirmed facts from assumptions. Never treat a diff, commit, green local test, or card status alone as proof of the user's full acceptance criteria. Do not publish, deploy, or enable broad approvals without explicit authorization.
